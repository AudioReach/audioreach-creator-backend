# Port ID Generation — Design

**Status:** Draft
**Owner:** Nithin Simon
**Feature folder:** `docs/edit-crud/`

---

## 1. Problem

`PatchSpfModuleHandler.applyDataPortCountChange` and `applyControlPortCountChange` resolve *how many* ports to add or remove, but have no mechanism to compute the `dataPortId` / `portId` natural identifier for newly-created dynamic ports. This design fills that gap with a shared, reusable calculator and a configuration read path.

---

## 2. Requirements

| ID | Requirement |
|----|-------------|
| FR-PORTID-01 | The `dataPortId` for a new dynamic data port is the **first unused ID** in the direction's canonical sequence for that module. Sequence depends on `portStrategy` (see §4.1). |
| FR-PORTID-02 | When adding N data ports in one call, assign the N lowest gaps. Each gap found for port k is treated as occupied when finding the gap for port k+1. |
| FR-PORTID-03 | The `portId` for a new dynamic control port is the first unused ID in the sequence `0x80000000, 0x80000001, 0x80000002, …` (always +1, no strategy influence). |
| FR-PORTID-04 | Static port IDs come from the module definition and are never generated by this logic. They are included in the occupied set to prevent collisions. |
| FR-PORTID-05 | The occupied set for a module's ports is **module-scoped** — port IDs on other modules are irrelevant. |
| FR-PORTID-06 | `portStrategy` for the file is read from the `configuration` table (`file_system_id → port_strategy`). If no row exists or the value is absent, `INPUT_EVEN_OUTPUT_ODD` is used as the default. |
| FR-PORTID-07 | The calculator functions are stateless pure functions in `@arc/core` with no infrastructure imports. |
| FR-PORTID-08 | `PatchSpfModuleHandler` is the primary consumer. `SpfModuleBuilder` (upload-file) and `AddModuleHandler` (add-module, static ports only today) are future secondary consumers. |

---

## 3. Design Decisions

### ADR-1: Port ID calculator location

**Context:** The calculator is stateless pure domain logic — it encodes AudioReach's port numbering rules. It needs to be importable by command handlers without pulling in infrastructure.

**Decision:** Place the calculator in the domain service layer:
`packages/core/src/domain/services/port-id-calculator/port-id-calculator.ts`

**Alternatives considered:**
- *Application `module/shared/`* — keeps it near `resolvePortCountChange`. But that file is orchestration logic (decides what changes to make); the calculator is a domain rule (what IDs are valid). Mixing the two blurs the layer boundary.
- *Inline in the handler* — simplest short-term; prevents reuse by upload-file and untestable in isolation.

**Prerequisites:** `ModulePortStrategy` / `MODULE_PORT_STRATEGIES` are currently defined in `application/file-operations/shared/awsp-serializers/v1/configuration/types.ts`. To allow the domain layer to import this type without violating the dependency rule (domain → application is forbidden), the type must be moved to `domain/entities/common/enums/module-port-strategy.ts`. Consumers (`SpfModuleBuilder`, `ConfigurationSchema` adapter, `@arc/core` barrel) update their import paths.

**Trade-offs:** One small prerequisite refactor (type move + import updates). Benefit: calculator and type live at the correct layer; upload-file can adopt the same function without circular imports.

---

### ADR-2: How the handler reads portStrategy

**Context:** The PATCH handler needs the `portStrategy` for the file inside its transaction. `portStrategy` is stored in the `configuration` table (one row per `fileSystemId`).

**Decision:** Add `getPortStrategy(fileSystemId: number): Promise<ModulePortStrategy>` to the existing `ProjectRepository` interface and implement it in `TypeOrmProjectRepository`.

`ProjectRepository` is already exposed via `uow.getProjectRepository()` — no UoW change needed. The `configuration` table row is created during the project-setup (upload) flow, so it is logically project-level data and belongs on the project repository.

**Alternatives considered:**
- *New `IFileConfigRepository`* — clean separation, but proliferates single-purpose interfaces for one method that is a natural extension of an existing repo.
- *Add to `IModuleEditRepository`* — portStrategy is not a module aggregate concept; wrong repo.
- *Pass via command* — leaks a persistence read to the controller tier.

**Trade-offs:** `ProjectRepository` gains its first read-only method, which slightly broadens its contract. Accepted because `configuration` is genuinely project-level data.

### 4.2 `PortIdCalculator` — pure domain functions

**File:** `packages/core/src/domain/services/port-id-calculator/port-id-calculator.ts`

```typescript
/*
 * Copyright (c) Qualcomm Technologies, Inc. and/or its subsidiaries.
 * SPDX-License-Identifier: BSD-3-Clause
 */

import {
  MODULE_PORT_STRATEGIES,
  type ModulePortStrategy,
} from '../../entities/common/enums/module-port-strategy.js';

export const MODULE_CONTROL_PORT_START = 0x80000000;

/**
 * Returns the N lowest data port IDs not already present in existingIds,
 * following the direction's canonical sequence for the given strategy.
 *
 * Sequences:
 *   INPUT_EVEN_OUTPUT_ODD — input:  2, 4, 6, 8, …  (start 2, +2)
 *                           output: 1, 3, 5, 7, …  (start 1, +2)
 *   SEQUENTIAL             — both:  1, 2, 3, 4, …  (start 1, +1)
 *
 * Gap-filling: if port IDs 2 and 3 were removed from a SEQUENTIAL module
 * that had {1,2,3,4,5}, and N=2 is requested, returns [2, 3] — not [6, 7].
 *
 * existingIds must include both static and dynamic port IDs for the
 * given direction on this module (module-scoped, not global).
 */
export function nextDataPortIds(
  existingIds: ReadonlySet<number>,
  isInput: boolean,
  strategy: ModulePortStrategy,
  count: number,
): number[] {
  const start = dataPortStartId(isInput, strategy);
  const increment = dataPortIncrement(strategy);
  const allocated = new Set(existingIds);
  const result: number[] = [];

  for (let i = 0; i < count; i++) {
    let id = start;
    while (allocated.has(id)) id += increment;
    allocated.add(id);
    result.push(id);
  }

  return result;
}

/**
 * Returns the N lowest control port IDs not already present in existingIds.
 * Sequence: 0x80000000, 0x80000001, 0x80000002, … (always +1).
 * Strategy has no effect on control port IDs.
 *
 * existingIds must include ALL control port IDs on this module (static and
 * dynamic, module-scoped).
 */
export function nextControlPortIds(
  existingIds: ReadonlySet<number>,
  count: number,
): number[] {
  const allocated = new Set(existingIds);
  const result: number[] = [];

  for (let i = 0; i < count; i++) {
    let id = MODULE_CONTROL_PORT_START;
    while (allocated.has(id)) id++;
    allocated.add(id);
    result.push(id);
  }

  return result;
}

// ── Internal helpers ──────────────────────────────────────────────────────────

function dataPortStartId(isInput: boolean, strategy: ModulePortStrategy): number {
  if (strategy === MODULE_PORT_STRATEGIES.INPUT_EVEN_OUTPUT_ODD) {
    return isInput ? 2 : 1;
  }
  return 1; // SEQUENTIAL — same start for both directions
}

function dataPortIncrement(strategy: ModulePortStrategy): number {
  return strategy === MODULE_PORT_STRATEGIES.INPUT_EVEN_OUTPUT_ODD ? 2 : 1;
}
```

Export from `packages/core/src/index.ts`:
```typescript
export {
  nextDataPortIds,
  nextControlPortIds,
  MODULE_CONTROL_PORT_START,
} from './domain/services/port-id-calculator/port-id-calculator.js';
```

```typescript
async getPortStrategy(fileSystemId: number): Promise<ModulePortStrategy> {
  const rows = await this.manager.query(
    `SELECT port_strategy FROM configuration WHERE file_system_id = ?`,
    [fileSystemId],
  );
  // Default: INPUT_EVEN_OUTPUT_ODD when no configuration row exists.
  return rows[0]?.port_strategy ?? MODULE_PORT_STRATEGIES.INPUT_EVEN_OUTPUT_ODD;
}
```

### 4.4 `PatchSpfModuleHandler` integration

**Strategy loading** — loaded once per handler invocation, lazily (only when a port count field is present):

```typescript
async handle(command: PatchSpfModuleCommand, uow: UnitOfWork): Promise<Result<WriteResult>> {
  await uow.startTransaction();

  const needsPortStrategy =
    command.maxInputPortsSupported !== undefined ||
    command.maxOutputPortsSupported !== undefined ||
    command.maxControlPortsSupported !== undefined;

  // One DB read, shared by all three applyXxxPortCountChange calls in this invocation.
  const portStrategy = needsPortStrategy
    ? await uow.getProjectRepository().getPortStrategy(command.fileSystemId)
    : undefined;

  // ... module existence check, load module ...

  if (command.maxInputPortsSupported !== undefined) {
    const result = await this.applyDataPortCountChange(
      module, PORT_IO_TYPE.Input, command.maxInputPortsSupported, portStrategy!, uow,
    );
    if (result.kind === RESULT_KIND.Fail) { await uow.rollback(); return result; }
  }
  // ... same for Output and ControlPort ...
}
```

**`applyDataPortCountChange` — additions using the calculator:**

```typescript
private async applyDataPortCountChange(
  module: SpfModule,
  ioType: PortIoType,
  requested: number,
  strategy: ModulePortStrategy,
  uow: UnitOfWork,
): Promise<Result<void>> {
  const isInput = ioType === PORT_IO_TYPE.Input;
  const currentPorts = module.dataPorts.filter(p => p.portIoType === ioType);

  // ... link check, resolvePortCountChange, removals (unchanged) ...

  if (outcome.data.toAdd > 0) {
    // existingIds: all data port IDs of this direction on this module (static + dynamic)
    const existingIds = new Set(currentPorts.map(p => p.dataPortId));
    const newPortIds = nextDataPortIds(existingIds, isInput, strategy, outcome.data.toAdd);

    for (const dataPortId of newPortIds) {
      const port = new DataPort({
        systemId: await this.idGeneration.getNextId(module.fileSystemId),
        dataPortId,
        portIoType: ioType,
        isStatic: false,
        name: `${isInput ? 'Input' : 'Output'}_${dataPortId}`,
      });
      await moduleRepo.addDataPort(port, module.systemId, uow);
    }
  }

  return Result.ok(undefined);
}
```

**`applyControlPortCountChange` — additions using the calculator:**

```typescript
if (outcome.data.toAdd > 0) {
  // existingIds: ALL control port IDs on this module (static + dynamic)
  const existingIds = new Set(module.controlPorts.map(p => p.portId));
  const newPortIds = nextControlPortIds(existingIds, outcome.data.toAdd);

  for (const portId of newPortIds) {
    // Intent availability check (REQ-PATCH-CTRL-04) runs before this block — unchanged.
    const port = new ControlPort({
      systemId: await this.idGeneration.getNextId(module.fileSystemId),
      portId,
      isStatic: false,
      nodeSystemId: module.systemId,
      name: `ControlPort_0x${portId.toString(16)}`,
      intentSystemIds: [],
    });
    await moduleRepo.addControlPort(port, module.systemId, uow);
  }
}
```

## 5. Data Flow

```
PATCH handler invoked
  │
  ├─ port count field present?
  │     └─ YES → uow.getProjectRepository().getPortStrategy(fileSystemId)
  │                        ↓
  │              SELECT port_strategy FROM configuration
  │
  ├─ applyDataPortCountChange(module, direction, requested, strategy, uow)
  │     │
  │     ├─ currentPorts = module.dataPorts filtered by direction
  │     ├─ resolvePortCountChange(...) → {toAdd, toRemove}
  │     ├─ removals: moduleRepo.removeDataPort(...)
  │     └─ additions:
  │           existingIds = Set(currentPorts.map(p => p.dataPortId))
  │           newIds = nextDataPortIds(existingIds, isInput, strategy, toAdd)
  │                         ↓
  │                   gap-fill in sequence (pure function, no I/O)
  │           for each id: new DataPort → moduleRepo.addDataPort(...)
  │
  └─ applyControlPortCountChange(module, requested, uow)
        │
        ├─ resolvePortCountChange(...)
        ├─ removals: moduleRepo.removeControlPort(...)
        └─ additions:
              existingIds = Set(module.controlPorts.map(p => p.portId))
              newIds = nextControlPortIds(existingIds, toAdd)
                            ↓
                      gap-fill from 0x80000000 (pure function, no I/O)
              for each id: new ControlPort → moduleRepo.addControlPort(...)
```

## 7. Requirements–Design Alignment

| FR | Design element |
|----|----------------|
| FR-PORTID-01 | `nextDataPortIds` — gap-fills in direction sequence |
| FR-PORTID-02 | Inner loop in `nextDataPortIds` adds each found ID to `allocated` before next iteration |
| FR-PORTID-03 | `nextControlPortIds` — gap-fills from `0x80000000`, +1 always |
| FR-PORTID-04 | Both functions accept a `ReadonlySet<number>` that includes static port IDs |
| FR-PORTID-05 | Caller builds `existingIds` from `module.dataPorts` / `module.controlPorts` (module-scoped) |
| FR-PORTID-06 | `ProjectRepository.getPortStrategy` reads `configuration` table |
| FR-PORTID-07 | `port-id-calculator.ts` imports only domain types, no infra |
| FR-PORTID-08 | Handler integration in §4.4; upload-file path is a secondary consumer (no change in this design) |
