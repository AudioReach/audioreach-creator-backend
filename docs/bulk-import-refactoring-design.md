## 1. Executive Summary

### Problem Statement
The current bulk import system uses an **Insert + Query Pattern** that requires querying the database after every insert to retrieve auto-generated systemIds. This results in:
- **100% overhead** in database operations (2x the necessary operations)
- **Complex query-back correlation logic** that is error-prone
- **Ambiguous two-state success model** that confuses consumers
- **Entity-specific implementations** with high code duplication

### Proposed Solution
Refactor to a **Direct Insert Pattern** with:
- **User-provided systemIds** eliminating the need for query-back
- **Generic N-level hierarchical processor** supporting unlimited hierarchy depth
- **Three-state status model** (SUCCESS, PARTIAL_SUCCESS, FAILED) for clarity
- **Configuration-based approach** eliminating code duplication

### Key Metrics

| Metric | Current | Proposed | Improvement |
|--------|---------|----------|-------------|
| DB Operations | 4 (2 inserts + 2 queries) | 2 (2 inserts) | **50% reduction** |
| Processing Time | ~200ms | ~100ms | **50% faster** |
| Code Lines | ~500 per entity | ~200 generic | **60% reduction** |
| Code Duplication | High | None | **100% elimination** |
| Hierarchy Support | 2 levels fixed | N levels | **Unlimited** |

## 2. Background & Context

### 2.1 Current System Overview

The bulk import system handles insertion of hierarchical entities (e.g., KeyDefinition → ValueDefinition) with the following characteristics:

- **Auto-generated SystemIds**: Database generates systemId via auto-increment
- **Natural Keys**: Entities have business keys (keyId, valueId) separate from systemId
- **Parent-Child Relationships**: Children reference parent via systemId foreign key
- **Batch Processing**: Multiple entities inserted in batches for performance

### 2.2 New Requirement

**Change:** SystemIds will now be **provided by users** instead of being auto-generated by the database.

**Rationale:**
- Users need control over systemId values for data management
- Enables deterministic IDs for testing and debugging
- Supports data migration and import scenarios
- Allows pre-allocation of ID ranges across systems
- Facilitates data synchronization between environments

### 2.3 Impact

This requirement change makes the current Insert + Query pattern obsolete, as we no longer need to query back to discover systemIds—they're already known from the input.

## 3. Current Approach: Insert + Query Pattern

### 3.1 Pattern Description

The **Insert + Query Pattern** is a two-phase approach:

1. **Insert Phase**: Insert entities without systemId (DB auto-generates)
2. **Query Phase**: Query back using natural keys to retrieve systemIds

```
┌─────────────────────────────────────────────────────────────┐
│              CURRENT: INSERT + QUERY PATTERN                 │
└─────────────────────────────────────────────────────────────┘

Input: Entities WITHOUT systemId (Omit<Entity, 'systemId'>)
  │
  ├─► Step 1: Map to partial rows (exclude systemId)
  │            Type: QueryDeepPartialEntity<EntityRow>
  │
  ├─► Step 2: Batch INSERT into database
  │            DB Operation #1: INSERT INTO Entity ...
  │            (Database auto-generates systemId)
  │
  ├─► Step 3: Query back using natural keys
  │            DB Operation #2: SELECT systemId, naturalKey FROM Entity WHERE ...
  │            (Retrieve auto-generated systemIds)
  │
  ├─► Step 4: Correlate query results with input
  │            Build Map: naturalKey → systemId
  │
  ├─► Step 5: Repeat for child entities
  │            Use parent systemIds as foreign keys
  │            DB Operations #3 & #4: INSERT + SELECT for children
  │
  └─► Output: Mappings (naturalId → systemId) + Errors
```

### 3.2 Current Implementation Example

**File: `key-definition.inserter.ts`**

```typescript
export class KeyDefinitionInserter extends BaseInserter<
  Omit<KeyDefinition, 'systemId'>,  // ❌ Partial entity input
  BulkKeyDefinitionInsertResult,
  KeyDefinitionInsertErrorEntity
> {
  async insert(
    keys: readonly Omit<KeyDefinition, 'systemId'>[]  // ❌ No systemId
  ): Promise<BulkKeyDefinitionInsertResult> {

    // ============================================
    // Phase 1: Insert Keys (without systemId)
    // ============================================
    const keyRows = keys.map(k => toKeyRow(k));  // Maps to partial row
    // Type: QueryDeepPartialEntity<KeyDefinitionRow>[]

    const keyInsertResult = await BatchInserter.insert(
      this.manager,
      'KeyDefinition',
      keyRows
    );
    // DB Operation #1: INSERT INTO KeyDefinition (keyId, keyName, ...)
    //                  VALUES (100, 'AUDIO_MODE', ...)
    // Database generates systemId = 1001

    // ============================================
    // Phase 2: Query Back Key SystemIds ❌
    // ============================================
    const successfulKeyIds = keyInsertResult.succeeded.map(
      row => row.keyId as number
    );

    const keyMappings = await this.queryBackKeys(successfulKeyIds);
    // DB Operation #2: SELECT systemId, keyId
    //                  FROM KeyDefinition
    //                  WHERE keyId IN (100, 101, 102)
    // Result: [{ systemId: 1001, keyId: 100 }, ...]

    // Build lookup map
    const keyIdToSystemId = new Map(
      keyMappings.map(m => [m.naturalId, m.systemId])
    );
    // Map: { 100 → 1001, 101 → 1002, ... }

    // ============================================
    // Phase 3: Insert Values (using parent systemIds)
    // ============================================
    const valueRowsWithKeyId: Array<{
      row: QueryDeepPartialEntity<ValueDefinitionRow>;
      keyId: number;
    }> = [];

    for (const key of keys) {
      const keySystemId = keyIdToSystemId.get(key.keyId);
      if (!keySystemId) continue;  // Parent failed

      for (const value of key.values) {
        valueRowsWithKeyId.push({
          row: toValueRow(value, keySystemId),  // Use parent systemId as FK
          keyId: key.keyId
        });
      }
    }

    const valueInsertResult = await BatchInserter.insert(
      this.manager,
      'ValueDefinition',
      valueRowsWithKeyId.map(v => v.row)
    );
    // DB Operation #3: INSERT INTO ValueDefinition
    //                  (valueId, valueName, keySystemId, ...)
    //                  VALUES (1, 'NORMAL', 1001, ...)
    // Database generates systemId = 2001

    // ============================================
    // Phase 4: Query Back Value SystemIds ❌
    // ============================================
    const valueMappings = await this.queryBackValuesComposite(
      valueRowsWithKeyId,
      valueInsertResult.succeeded
    );
    // DB Operation #4: SELECT systemId, valueId, keySystemId
    //                  FROM ValueDefinition
    //                  WHERE valueId IN (1, 2, 3)
    //                    AND keySystemId IN (1001, 1002)
    // Result: [{ systemId: 2001, valueId: 1, keySystemId: 1001 }, ...]

    // ============================================
    // Phase 5: Build Results
    // ============================================
    return this.buildResultsOptimized(
      keys,
      keyIdToSystemId,
      valueMappingsByKey,
      keyInsertResult,
      valueInsertResult
    );
  }

  // ❌ Complex query-back method
  private async queryBackKeys(
    keyIds: number[]
  ): Promise<NaturalIdMapping<number>[]> {
    if (keyIds.length === 0) return [];

    const results = await this.manager
      .createQueryBuilder('KeyDefinition', 'k')
      .select(['k.systemId', 'k.keyId'])
      .where('k.keyId IN (:...ids)', { ids: keyIds })
      .getMany();

    return results.map(r => ({
      naturalId: r.keyId,
      systemId: r.systemId
    }));
  }

  // ❌ Even more complex composite key query
  private async queryBackValuesComposite(
    valueRowsWithKeyId: Array<{
      row: QueryDeepPartialEntity<ValueDefinitionRow>;
      keyId: number;
    }>,
    succeededRows: QueryDeepPartialEntity<ValueDefinitionRow>[]
  ): Promise<Array<{mapping: NaturalIdMapping<number>; keyId: number}>> {
    if (succeededRows.length === 0) return [];

    const keySystemIds = [
      ...new Set(succeededRows.map(row => row.keySystemId as number))
    ];
    const valueIds = [
      ...new Set(succeededRows.map(row => row.valueId as number))
    ];

    const results = await this.manager
      .createQueryBuilder('ValueDefinition', 'v')
      .select(['v.systemId', 'v.valueId', 'v.keySystemId'])
      .where('v.valueId IN (:...valueIds)', { valueIds })
      .andWhere('v.keySystemId IN (:...keySystemIds)', { keySystemIds })
      .getMany();

    // Complex correlation logic to map back to original context...
    // ...
  }
}
```

**Total Database Operations: 4 (2 inserts + 2 queries)**

### 3.3 Current Approach Issues

#### 3.3.1 Performance Issues

| Issue | Description | Impact |
|-------|-------------|--------|
| **Query Overhead** | 2 extra queries per hierarchy level | 100% overhead (doubles DB operations) |
| **Latency** | Each query adds 50-100ms | Cumulative delay in bulk operations |
| **Network Round-trips** | Additional database round-trips | Increased latency in distributed systems |
| **Query Complexity** | Complex WHERE clauses with IN operators | Slower query execution for large batches |
| **Scalability** | Query overhead grows with hierarchy depth | Poor performance for deep hierarchies |

**Example:**
```
100 KeyDefinitions + 500 ValueDefinitions
Current: 4 DB operations (~200ms)
- Insert 100 keys: 50ms
- Query 100 systemIds: 50ms  ❌ Unnecessary
- Insert 500 values: 75ms
- Query 500 systemIds: 75ms  ❌ Unnecessary
```

#### 3.3.2 Code Complexity Issues

| Issue | Description | Impact |
|-------|-------------|--------|
| **Type Complexity** | `Omit<>`, `QueryDeepPartialEntity<>` | Hard to understand, error-prone |
| **Correlation Logic** | Must match query results to input | Complex, fragile code |
| **Error Handling** | Query failures can break entire operation | Fragile despite successful inserts |
| **Duplication** | Each entity type needs own inserter | High maintenance burden |
| **Testing** | Must test insert + query + correlation | Complex test scenarios |

#### 3.3.3 Semantic Issues

| Issue | Description | Impact |
|-------|-------------|--------|
| **Two-State Logic** | Boolean `success` with errors | Ambiguous semantics |
| **Unclear Handling** | What to do with `success: true` + errors? | Poor consumer experience |
| **Lost Information** | Cannot distinguish full vs partial success | Suboptimal decision making |

**Example of Ambiguity:**
```typescript
{
  success: true,  // ❓ Is this really success?
  errors: [
    { entity: 'ValueDefinition', naturalId: '5', code: 'UNIQUE_CONSTRAINT' }
  ]
}
// Questions:
// - Should I use the data?
// - Should I retry the failed value?
// - Is this a warning or an error?
```

## 4. Proposed Approach: Direct Insert Pattern

### 4.1 Pattern Description

The **Direct Insert Pattern** eliminates query-back by using user-provided systemIds:

```
┌─────────────────────────────────────────────────────────────┐
│              PROPOSED: DIRECT INSERT PATTERN                 │
└─────────────────────────────────────────────────────────────┘

Input: Complete entities WITH systemId
  │
  ├─► Step 1: Build hierarchical tree structure
  │            Organize entities by parent-child relationships
  │            SystemIds already known from input
  │
  ├─► Step 2: Insert level-by-level (breadth-first)
  │            Level 0: Batch INSERT parents
  │            DB Operation #1: INSERT INTO Parent ...
  │
  │            Level 1: Batch INSERT children (using parent systemIds)
  │            DB Operation #2: INSERT INTO Child ...
  │
  │            Level N: Continue for deeper hierarchies
  │
  ├─► Step 3: Build mappings directly from input
  │            No query needed - systemIds from input
  │            Map: naturalKey → systemId (from input)
  │
  └─► Output: Mappings + Errors (with three-state status)
```

### 4.2 Result Type Definitions

Before showing the implementation, let's understand the result types:

#### HierarchicalBulkInsertResult

```typescript
/**
 * Result of bulk hierarchical insert operation.
 * Contains an array of results, one per root entity.
 */
export interface HierarchicalBulkInsertResult {
  /** Array of results, one for each root entity that was attempted to insert */
  results: HierarchicalInsertResult[];
}
```

**Purpose**: Wraps multiple entity results when inserting a batch of root entities.

**Example**:
```typescript
// Inserting 3 KeyDefinitions
const result: HierarchicalBulkInsertResult = {
  results: [
    { /* Result for KeyDefinition 1 */ },
    { /* Result for KeyDefinition 2 */ },
    { /* Result for KeyDefinition 3 */ }
  ]
};
```

#### HierarchicalInsertResult

```typescript
/**
 * Result for a single root entity and its entire hierarchy.
 * Includes mappings for the root and all descendants, plus any errors.
 */
export interface HierarchicalInsertResult {
  /** Root entity mapping (naturalId → systemId) */
  mapping?: NaturalIdMapping;

  /**
   * Child mappings organized by entity type.
   * Key: Entity name (e.g., 'ValueDefinition', 'Calibration')
   * Value: Array of mappings for that entity type
   */
  childMappings: Record<string, NaturalIdMapping[]>;

  /** All errors that occurred in this hierarchy (root + all descendants) */
  errors: InsertError[];

  /** Three-state status indicating overall success */
  status: InsertStatus;  // 'SUCCESS' | 'PARTIAL_SUCCESS' | 'FAILED'
}
```

**Purpose**: Represents the complete result for one root entity and all its children/descendants.

**Structure Breakdown**:

1. **`mapping`**: Root entity's naturalId → systemId mapping
   - Present if root entity inserted successfully
   - Undefined if root entity failed

2. **`childMappings`**: Organized by entity type for easy lookup
   - Key = entity name (e.g., 'ValueDefinition')
   - Value = array of mappings for that entity type
   - Only includes successfully inserted children

3. **`errors`**: Complete error list for this hierarchy
   - Includes root errors (if root failed)
   - Includes child errors (if any children failed)
   - Each error identifies which entity failed

4. **`status`**: Three-state indicator
   - `'SUCCESS'`: Root and all children succeeded
   - `'PARTIAL_SUCCESS'`: Root succeeded, some children failed
   - `'FAILED'`: Root failed (children not attempted)

**Complete Example**:
```typescript
// Example: KeyDefinition with 3 ValueDefinitions (1 fails)
const result: HierarchicalInsertResult = {
  // Root mapping (KeyDefinition succeeded)
  mapping: {
    naturalId: 100,    // keyId
    systemId: 1001     // systemId from user input
  },

  // Child mappings by entity type
  childMappings: {
    'ValueDefinition': [
      { naturalId: 1, systemId: 2001 },  // Value 1 succeeded
      // Value 2 missing - it failed
      { naturalId: 3, systemId: 2003 }   // Value 3 succeeded
    ]
  },

  // Errors (only for failed entities)
  errors: [
    {
      entity: 'ValueDefinition',
      naturalId: '2',
      code: 'UNIQUE_CONSTRAINT',
      message: 'UNIQUE constraint failed: ValueDefinition.valueId',
      causes: []
    }
  ],

  // Status reflects partial success
  status: 'PARTIAL_SUCCESS'
};
```

#### NaturalIdMapping

```typescript
/**
 * Maps a natural key to its systemId.
 * Used to correlate business identifiers with database identifiers.
 */
export interface NaturalIdMapping<TKey = number> {
  /** Natural identifier (business key) from the domain entity */
  naturalId: TKey;

  /** System identifier (database primary key) */
  systemId: number;
}
```

**Purpose**: Links business keys (keyId, valueId) to database keys (systemId).

**Example**:
```typescript
const mapping: NaturalIdMapping = {
  naturalId: 100,   // keyId from domain
  systemId: 1001    // systemId in database
};
```

### 4.3 Proposed Implementation Example

**File: `n-level-hierarchical-inserter.ts` (New Generic Implementation)**

```typescript
export class NLevelHierarchicalInserter {
  constructor(private manager: EntityManager) {}

  async insert<TRoot>(
    entities: TRoot[],  // ✅ Complete entities WITH systemId
    definition: HierarchyDefinition<TRoot>
  ): Promise<HierarchicalBulkInsertResult> {

    if (entities.length === 0) {
      return { results: [] };
    }

    // ============================================
    // Step 1: Build Tree Structure
    // ============================================
    const trees = this.buildTrees(entities, definition);
    // Tree structure with systemIds already known:
    // {
    //   entity: KeyDefinition,
    //   systemId: 1001,  ✅ From input
    //   naturalKey: 100,
    //   children: [
    //     { entity: ValueDefinition, systemId: 2001, ... },
    //     { entity: ValueDefinition, systemId: 2002, ... }
    //   ]
    // }

    // ============================================
    // Step 2: Insert Level-by-Level
    // ============================================
    await this.processLevelByLevel(trees);
    // Level 0: Insert all KeyDefinitions
    // DB Operation #1: INSERT INTO KeyDefinition
    //                  (systemId, keyId, keyName, ...)
    //                  VALUES (1001, 100, 'AUDIO_MODE', ...)
    // ✅ SystemId provided by user, no query needed!

    // Level 1: Insert all ValueDefinitions
    // DB Operation #2: INSERT INTO ValueDefinition
    //                  (systemId, valueId, valueName, keySystemId, ...)
    //                  VALUES (2001, 1, 'NORMAL', 1001, ...)
    // ✅ SystemId provided by user, no query needed!

    // ============================================
    // Step 3: Build Results (from input data)
    // ============================================
    return this.buildResults(trees);
    // Mappings built directly from input:
    // {
    //   mapping: { naturalId: 100, systemId: 1001 },  ✅ From input
    //   childMappings: {
    //     'ValueDefinition': [
    //       { naturalId: 1, systemId: 2001 },  ✅ From input
    //       { naturalId: 2, systemId: 2002 }   ✅ From input
    //     ]
    //   },
    //   errors: [],
    //   status: 'SUCCESS'  ✅ Three-state status
    // }
  }
}
```

**Total Database Operations: 2 (2 inserts only, 0 queries)**
**Performance Improvement: 50% reduction in DB operations**

## 6. Three-State Status Model

### 6.1 Status Definition

```typescript
export type InsertStatus = 'SUCCESS' | 'PARTIAL_SUCCESS' | 'FAILED';
```

### 6.2 Status Determination Logic

| Condition | Status | Meaning |
|-----------|--------|---------|
| Root entity failed to insert | `FAILED` | Cannot proceed with children, entire aggregate failed |
| Root succeeded, all children succeeded | `SUCCESS` | Complete success, all data usable |
| Root succeeded, some children failed | `PARTIAL_SUCCESS` | Root usable, but some children missing |

### 6.3 Status Examples

**Example 1: Full Success**
```typescript
{
  mapping: { naturalId: 100, systemId: 1001 },
  childMappings: {
    'ValueDefinition': [
      { naturalId: 1, systemId: 2001 },
      { naturalId: 2, systemId: 2002 }
    ]
  },
  errors: [],
  status: 'SUCCESS'  // ✅ Everything succeeded
}
```

**Example 2: Partial Success**
```typescript
{
  mapping: { naturalId: 100, systemId: 1001 },  // ✅ Parent succeeded
  childMappings: {
    'ValueDefinition': [
      { naturalId: 1, systemId: 2001 },  // ✅ Child 1 succeeded
      // Child 2 missing - it failed ❌
    ]
  },
  errors: [
    {
      entity: 'ValueDefinition',
      naturalId: '2',
      code: 'UNIQUE_CONSTRAINT',
      message: 'Duplicate value constraint violation'
    }
  ],
  status: 'PARTIAL_SUCCESS'  // ⚠️ Parent succeeded, but 1 child failed
}
```

```typescript
  const hasChildErrors = allErrors.some(e => e.entity !== parentNode.entityName);

  return 'SUCCESS';  // All children succeeded
```

```typescript
// ✅ Remove QueryDeepPartialEntity import

/**
 * Result of a batch insert operation.
 * Separates successfully inserted rows from failed rows with their errors.
 */
export interface BatchInsertResult<TRow> {
  /** Array of rows that were successfully inserted */
  succeeded: TRow[];

  /** Array of rows that failed to insert, along with their error details */
  failed: Array<{
    row: TRow;      // The row that failed to insert
    error: Error;   // The error that occurred during insertion
  }>;
}

export const BatchInserter = {
  /**
   * Batch insert entities with automatic fallback to individual inserts on failure.
   *
   * Algorithm:
   * 1. Try to insert entire batch at once (fast path)
   * 2. If batch fails, retry each row individually (slow path)
   * 3. This isolates which specific rows caused failures
   *
   * @param manager - TypeORM entity manager
   * @param target - Entity target (class or table name)
   * @param rows - Complete entity rows to insert (with systemId)
   * @param batchSize - Number of rows per batch (default: 100)
   * @returns Result with succeeded and failed rows
   */
  async insert<TEntity extends ObjectLiteral>(
    manager: EntityManager,
    target: EntityTarget<TEntity>,
    rows: TEntity[],  // ✅ Complete entities
    batchSize = 100,
  ): Promise<BatchInsertResult<TEntity>> {  // ✅ Simple type
    const succeeded: TEntity[] = [];
    const failed: Array<{row: TEntity; error: Error}> = [];

    for (let i = 0; i < rows.length; i += batchSize) {
      const batch = rows.slice(i, i + batchSize);
      try {
        // Fast path: try batch insert
        await manager.insert<TEntity>(target, batch);
        succeeded.push(...batch);
      } catch {
        // Slow path: retry individually to isolate failures
        for (const row of batch) {
          try {
            await manager.insert<TEntity>(target, row);
            succeeded.push(row);
          } catch (rowError) {
            failed.push({row, error: rowError as Error});
          }
        }
      }
    }

    return {succeeded, failed};
  }
};
```

```typescript
/**
 * Utility functions for error handling in bulk insert operations.
 * Used by NLevelHierarchicalInserter and other inserters.
 */
export class InsertErrorUtils {
  /**
   * Build domain-oriented error from exception.
   */
  static buildError<TErrorEntity extends string>(
    entity: TErrorEntity,
    naturalId: string | number,
    error: Error,
  ): InsertError<TErrorEntity> {
    return {
      entity,
      naturalId: String(naturalId),
      code: this.classifyError(error),
      message: error.message,
      causes: this.extractCauses(error),
    };
  }

  /**
   * Classify error into domain error codes.
   */
  static classifyError(error: Error): string {
    const message = error.message.toLowerCase();

    if (message.includes('unique constraint') || message.includes('unique')) {
      return 'UNIQUE_CONSTRAINT';
    }
    if (message.includes('foreign key') || message.includes('fk')) {
      return 'FK_VIOLATION';
    }
    if (message.includes('not null') || message.includes('null')) {
      return 'NULL_CONSTRAINT';
    }
    if (message.includes('check constraint')) {
      return 'CHECK_CONSTRAINT';
    }

    return 'INSERT_FAILED';
  }

  /**
   * Extract nested error causes if available.
   */
  static extractCauses(
    error: Error,
  ): Array<{code: string; message: string}> {
    const causes: Array<{code: string; message: string}> = [];

    if ('cause' in error && error.cause instanceof Error) {
      causes.push({
        code: this.classifyError(error.cause),
        message: error.cause.message,
      });
    }

    return causes;
  }
}
```
